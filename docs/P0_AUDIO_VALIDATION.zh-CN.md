## 复现步骤

在项目根目录 PowerShell 中使用独立环境：

```powershell
.\.venv\Scripts\python.exe tools\audio_diagnostics.py --output docs\P0_AUDIO_ENVIRONMENT.json
```

安装并重启后，重新枚举，从 JSON 中复制准确的虚拟播放端点 ID，然后在向该虚拟设备播放固定测试素材时运行：

```powershell
.\.venv\Scripts\python.exe tools\audio_diagnostics.py --capture --source-id '<准确 ID>' --seconds 5 --output docs\P0_AUDIO_CAPTURE.json
```

分别在 Windows 音量 100、50、10、0 和静音下重复记录至不同文件，核对 RMS 趋势。不要将设备成功枚举或 recorder 打开视为音量、HomePod 播放及延迟已经通过。

采集被静默端点阻塞时，诊断在时限外最多额外等待 5 秒并报告 timed_out；此结果本身不证明驱动故障。退出码 0 表示枚举或采集探测完成，2 表示环境阻碍、采集失败或超时；命令参数错误也为 2。

## Windows 音量验证：发现兼容性问题

已安装并锁定 pycaw 20260927、comtypes 1.4.17。SoundCard 使用 MTA，comtypes 默认 STA，混用会出现 RPC_E_CHANGED_MODE；诊断工具已在导入前设置 `sys.coinit_flags = 0`。

新增 `tools/probe_cable_volume.py`，仅向明确指定的 VB-Audio 端点播放幅度 0.02 的测试音，逐档设置端点音量与静音、读取 loopback 的 RMS；使用 finally 恢复原状态。结果见 `P0_VOLUME_MEASUREMENTS.json`：

| Windows 设置 | 捕获 RMS |
| --- | --- |
| 100%，非静音 | 0.0113844 |
| 50%，非静音 | 0.0114409 |
| 10%，非静音 | 0.0114833 |
| 0%，非静音 | 0.0114049 |
| 100%，静音 | 0.0113752 |

当前配置下，Windows 音量和静音没有作用于采集信号。测试后读回的端点音量与静音均与测试前一致。尚未验证 VB-CABLE 控制面板的 Enable Windows Volume Control 状态；需要核对并启用该选项后重新测试。若启用后仍无效，采用计划中的显式软件音量兼容模式，并防止重复衰减。

### 用户启用驱动音量后的复测

用户确认启用 Enable Windows Volume Control。首次短音测试出现启动/调音过渡，随后将每档测试音延长到两秒、调音后等待 0.5 秒，并取采集缓冲中部统计，避免以过渡信号作结论。结果见 `P0_VOLUME_ENABLED_MEASUREMENTS.json`：100% RMS 0.0112931、50% 0.00527312、10% 0.000220887、0% 为零、静音为零。所有档位各测量 44,100 帧，原音量和静音恢复成功。

本机当前配置满足原生端点音量与静音要求，不添加额外 PCM 增益。该结论仅覆盖目前驱动选项与标准 CABLE Input loopback；其他版本/路径仍需验证。

### SSL 打包问题已修复

本机托管 Python 的 `ssl.SSLContext.__new__` 会加载标准库目录旁的 `codex-rejected-cas.pem`。冻结后缺少该资源，导致初始化报文件不存在。构建脚本已增加条件资源收集：仅在构建运行时存在此文件时，将它放入冻结根目录，保留原 TLS 行为。在普通 Python 构建环境不增加该资源。没有修改证书验证逻辑。

重新构建的 `dist/HomePodCast.exe` 已完成只读自检，退出码 0、`ok=true`，Tk/pyatv/COM/音频端点均可用，测试前后默认设备保持 Realtek。结果见 `P3_PACKAGED_RUNTIME.json`。CI 新增同样的打包运行时检查，允许无音频设备的 runner，但初始化或依赖失败必须使构建失败。

当前 EXE 可作为继续验收的开发构建，尚不表示完整生产验收通过。还缺：Windows 10/其他架构环境、真实多台音箱的掉线矩阵、休眠/音频服务重启、48 kHz 路径、端到端实测延迟、至少两小时稳定性，以及第二阶段驱动选型和原型。已通过的基础路径与音量结论不能扩大为这些项目已通过。

另发现 pycaw 的 COMError 不继承 OSError；已补全默认设备不存在与设备被移除时的异常处理。19 项回归测试通过，新增两项直接模拟真实 COMError 类型。最新 EXE 已重建并再次通过自检，SHA256 为 `739767DAC471B0423A6AE5A49717665EA90DB45B54C5CAD5950717537C447E33`。该文件不是已完成全部验收的正式发行版本。
